# Chess & Cards 代码审查报告

日期：2026-11-12　范围：全仓（packages / apps / services / infra / tools）
审查方式：分模块通读 + 关键结论逐条回源核实

---

## 一、总体结论

工程结构、协议分层、游戏插件抽象、UI 完成度都明显高于一般演示项目；服务端权威、只追加账本、幂等键这些骨架也是对的。问题集中在三类：

1. **默认配置 fail-open** —— 密钥、令牌缺失时用硬编码值照常启动，照 README 部署上线就是一个可被接管的系统。
2. **反作弊链路的断点** —— 验证码答案直接写在 SVG 里、限流信任伪造的 X-Forwarded-For、房间洗牌种子取自玩家可见的 `房间ID-局数`。三者叠加，防刷与牌局公平性基本失守。
3. **资金一致性只做了一半** —— 结算上报失败只重试 3 次就放弃，没有 outbox；部分路径静默把余额截断到 0；断线与中止分支存在「只给赢家加钱、不扣输家」的漏洞，可以凭空造币。

前端没有大包问题（JS 302KB / gzip 93KB），真正的负担是首屏约 **2.7MB 图片全量 eager 加载**，以及一个会让断线玩家牌桌永久冻结的重连缺陷。

### 问题统计

| 级别 | 数量 | 含义 |

## 二、P0 阻断问题

### P0-1　密钥与运营口令存在硬编码默认值，缺配置也不报错

**位置**：`apps/api-server/src/config.ts:23-30`、`services/room-server/src/config.ts:24-26`、`infra/.env.example`

三个敏感项都有可直接使用的兜底值：

```ts
jwtSecret: env('JWT_SECRET', 'dev-secret-change-me'),
internalKey: env('INTERNAL_KEY', 'dev-internal-key'),
adminToken: env('ADMIN_TOKEN', 'admin-dev-token'),
```

并且 `.env.example` 里**根本没有 `ADMIN_TOKEN` 这一项**，按文档部署的人不会去设置它。

**影响**：攻击者用 `dev-secret-change-me` 签发任意 `sub` 的 JWT，即可登录任何账号、改资料、动钱包；用 `admin-dev-token` 调用 GM 接口无限发筹码、发任意公告；用 `dev-internal-key` 直接 POST `/internal/settle` 凭空造币。

**改法**：生产环境 fail-fast，不要「警告后继续」。

```ts
function requireSecret(key: string): string {
  const v = process.env[key];
  if (!v || v.length < 32 || v.startsWith('dev-')) {
    throw new Error(`${key} 未配置或强度不足（需 ≥32 位随机字符），拒绝启动`);
  }
  return v;
}
// 开发态才允许兜底
const isProd = process.env.NODE_ENV === 'production';
jwtSecret: isProd ? requireSecret('JWT_SECRET') : env('JWT_SECRET', 'dev-secret-change-me'),
```

同时 `.env.example` 补上 `ADMIN_TOKEN=`，并在 `deploy.sh` 里检查 `.env` 三项长度。

### P0-2　验证码答案明文写在 SVG 文本节点里，等于没有验证码

**位置**：`apps/api-server/src/security.ts:56-63`（渲染）、`:95-98`（生成）

```ts
`<text ...>${answer[i]}</text>`   // 答案就是 SVG 里的可见字符
answer += CAPTCHA_CHARS[Math.floor(Math.random() * CAPTCHA_CHARS.length)];
```

脚本 `fetch('/api/captcha')` 后正则抽出 `<text>` 内容即可 100% 通过，配合 P0-3 的限流绕过，注册/登录爆破无成本。另外 `Math.random()` 本身可预测。

**改法**：短期把字符转成 path 轮廓再输出（`opentype.js` 或预置字形 path 表），或用噪点/扭曲干扰到 OCR 难以识别；字符生成换 `crypto.randomInt`；长期直接换第三方验证或滑块。若只是教学项目，至少加一层「验证码校验失败计数 + IP 封禁」。

### P0-3　IP 限流信任 X-Forwarded-For 首段，可任意伪造绕过

**位置**：`apps/api-server/src/index.ts:108-114`、`infra/nginx-lobby.conf:8`

```ts
return forwarded.split(',')[0]?.trim() ?? 'unknown';
```

nginx 侧若用 `$proxy_add_x_forwarded_for`，客户端自带的伪造值会被保留在最前面，取首段等于取攻击者自己填的值。每次请求换一个假 IP，登录/注册/验证码限流全部失效，还会把 limiter 的 Map 撑大。

**改法**：配置 Fastify `trustProxy` 为本机/具体代理地址，然后统一用 `req.ip`；或只取可信代理追加的最后一跳。

```ts
const app = Fastify({ logger: false, trustProxy: '127.0.0.1' });
// clientIp -> return req.ip
```

### P0-4　房间洗牌种子可由玩家推导，牌局可被提前算出

**位置**：`services/room-server/src/room.ts:239`

```ts
this.seed = `${this.id}-${this.round}`;
```

`roomId` 与局数 `round` 客户端都可见。`baccarat:129`、`dice:164`、`blackjack:336`、`niuniu:232`、`tuizhuanzi:141` 都拿它洗牌/开骰，玩家只要拿到种子就能复现整副牌或骰点，做到必赢。

**改法**：种子必须来自 CSPRNG，且永不下发给客户端、不进快照、不进日志。

```ts
import { randomBytes } from 'node:crypto';
this.seed = randomBytes(16).toString('hex');
```

### P0-5　结算上报无 outbox，失败即永久丢失

**位置**：`services/room-server/src/settlement.ts:12-38`

只在内存里重试 3 次（约 1.8s 退避），最终失败仅打一行「需人工补偿」日志。此时本金已经从玩家钱包扣掉（`ctx.charge`），客户端也已显示赢分，但账本没有入账。

部署、重启、网络抖动、api-server 短暂 502 都会触发。README 宣称「账务可信」，这里是链路上最薄的一环。

**改法**：本地持久化 outbox（SQLite 或 JSONL 落盘即可），按 `settlementId` 幂等重投；进程优雅退出前等待队列清空；启动时重放未确认记录。同时补一个 GM 侧「查询未结算 settlementId」的接口，让「人工补偿」真正可执行。

### P0-6　每日排行榜在服务启动时无条件结算，且幂等键不含用户

**位置**：`apps/api-server/src/index.ts:874-891`、`repository/postgres.ts:475-491`

```ts
let settledDay = '';          // 只在内存
void settleDaily();           // 启动即执行，不等 0 点
```

两个问题：

- **时点错误**：每次重启都会按「当下余额」提前发一轮排行榜奖励，而不是按当日 23:59 的快照。
- **幂等键错误**：`credit(..., 'leaderboard_daily', \`${dayKey}:${index + 1}\`)` 里没有 `userId` 也没有 `settledDay` 落库。第一次调用（哪怕是上午重启）就把 `dayKey:rank` 用掉了，之后真正的 0 点结算无法给正确的人补发。

**改法**：把已结算日期落库（`job_state` 表或 `leaderboard_daily_settlements(period_key)` 唯一行），只有 `beijingDayKey()` 与库内值不同且当前时间已过 0 点才结算；幂等键改为 `${dayKey}:${userId}`。

## 三、P1 高危问题

### 资金与公平性

**P1-1　断线判负 / 人数不足中止只给赢家加钱，不扣输家 → 凭空造币**
`room.ts:695-700`（中止本局只置 `waiting`，不 settle、不 refund，本金冻结）、`room.ts:703-718`（断线先删座位再通知插件，`ctx.players` 已不含离场者，`gomoku:116`、`doudizhu:163` 的离场判负只给赢家加钱）。改法：中止时逐笔 refund；断线先 `onPlayerLeave` 再删座位，结算走统一入口。

**P1-2　余额更新用 `greatest(balance + $2, 0)` 静默截断，账本对不上**
`postgres.ts:260`、`postgres.ts:369`。扣款/结算时余额不足不会报错，直接被抹到 0，但 ledger 里记录的 `delta` 与 `balance_after` 不一致，事后无法对账；配合小号对刷可以低成本造币。改法：UPDATE 加 `and balance + $2 >= 0`，`rowCount === 0` 时抛错并回滚；仅「奖励类」入账可以保留截断逻辑。

**P1-3　打赏/扣款先读后写，并发可透支**
`index.ts:430-435` + `postgres.ts`。改法同上，单条原子 UPDATE。

**P1-4　下注 `await ctx.charge` 后不校验 phase/round**
`baccarat:265-273`、`dice:244-257`、`niuniu:182-194`、`blackjack:223-235`。`charge` 是异步的，await 期间封盘结算甚至 `beginRound` 可能已经发生，迟到的注落进新一局或不被结算，本金悬空。改法：await 之后复核 `phase` 与 `round`，不符立即 `refund`。

**P1-5　`/api/guest` 无验证码、无限流**
`index.ts:266-278`。脚本可批量建号拿初始筹码刷榜/撑库，每次还跑一次 scrypt 吃 CPU。改法：加 IP 限流 + 验证码，生产直接关闭。

### 可用性

**P1-6　救济金任务永远无法领取**
`tasks.ts:118-127` 定义了 `relief`（`target: 1`、`kind: 'relief'`），但全仓没有任何地方 bump 它的进度，`buildTasks` 得到的 `progress` 恒为 0，claim 时在 `index.ts:410` 必判「任务尚未完成」。改法：`relief` 不依赖进度，直接以 `balance < maxBalance` 作为可领取条件（`claimable = !claimed && !blocked`）。

**P1-7　机器人行动未 await，异常会打死进程**
`room.ts:451-463`：`this.handleIntent(...)` 是 async，却未 await 也未 catch，插件抛错会变成 `unhandledRejection`（Node 默认退出进程），且函数提前 `return true`。改法：`await this.handleIntent(...)` 并 catch。

**P1-8　detach 不校验 socket，多端登录互相踢下线**
`room.ts:480-489`：同账号双端时，旧页面关闭会执行 `detach(playerId)` 把当前有效连接置空，60s 后被踢出房间。改法：`detach(playerId, ws)`，仅 `seat.socket === ws` 时生效。

**P1-9　房间与定时器泄漏**
`room.ts:539-552`：非对局中最后一名真人离开、房里还有 bot 时不走 `checkEnoughPlayers`，房间和 200ms 定时器永不回收。改法：统一走一次回收检查。

**P1-10　前端断线重连后牌桌永久冻结**
`apps/lobby-web/src/ws.ts:74` 的 `setRoomRef` 已实现，但**全项目无人调用**（`App.tsx:198` 收到 `RoomView` 时没有设置）。重连后只收到 `hello`，不会重新 join 房间，快照停止，只能退回大厅。改法：

```ts
s.on(ServerMsg.RoomView, ({ room }) => {
  s.setRoomRef({ roomId: room.roomId, playerId: userIdRef.current! });
  // ...
});
// 离开房间时 setRoomRef(null)
```

**P1-11　WebSocket 层缺少基本防护**
`services/room-server/src/index.ts:112-114,334`：无 `maxPayload`（默认 100MB）、无 Origin 校验（任意网站都能连）、`listen(port)` 未指定 host 即监听 `0.0.0.0`（可绕过 nginx 直连 9000）、CORS `*`。改法：`new WebSocketServer({ maxPayload: 64 * 1024, verifyClient })` 校验 Origin 白名单；`listen(port, '127.0.0.1')`；CORS 改白名单。

**P1-12　`pnpm typecheck` 直接失败，唯一类型门禁不可用**
根目录没有 `tsconfig.json`（只有 `tsconfig.base.json`），各包 `noEmit` 且无 `composite`，`tsc -b --pretty` 无项目可建。改法：根建 `tsconfig.json` 用 `references` 串起各包，各包加 `"composite": true`。

### 安全

**P1-13　GM 口令走 URL query、非恒定时间比较、无失败限流**
`index.ts:653,713,754,777,790`、`tools/gm-tool.ps1:127,370`。口令会进 nginx access log 和代理历史；`!==` 比较可被时序探测；GM 工具默认站点还是明文 `http://…/lobby`。改法：改 `Authorization: Bearer` 头、`crypto.timingSafeEqual`、IP 白名单 + 失败限流、强制 HTTPS。

**附带同类项**：用户不存在时不跑 scrypt（`security.ts:19-25`），响应快一个数量级，可枚举账号 —— 不存在时跑一次哑散列；500 响应回传 `error.message`（`index.ts:250-260`），泄漏 SQL 与约束名 —— 生产固定文案，详情只进日志。

**P1-14　昵称可重名 + 头像随好友列表全量返回**
`index.ts:462-476`、`postgres.ts:681`：昵称无唯一约束，可冒名；头像以 base64 data URL 存在用户行里，好友/搜索接口全量返回，N 个好友 × 数百 KB。改法：昵称加唯一索引（或按需允许重名但加 #tag）；头像单独存 URL，列表接口只返回缩略图地址。

## 四、P2 中等问题

### 架构与重复

**P2-1　13 个游戏大量复制粘贴。** `baccarat`、`niuniu`、`dice`、`tuizhuanzi`、`blackjack` 共用同一组下注常量与「开盘—封盘—开奖—结算」流程；`goldenflower`、`stud`、`texas` 的状态机与加注/结算近乎逐行相同。建议在 `packages/game-sdk` 抽两个基类：`BettingPlugin`（phase 时间轴 + TicketBook + 机器人投注计划）和 `TurnPokerBase`（ante/raise/turn/settle），各游戏只保留牌型与开奖逻辑。这一项能消掉约 1000 行重复代码，也顺带修掉 P1-4 那类「每个游戏各自漏校验」的问题。

**P2-2　超长文件应拆分。** `api-server/src/index.ts` 903 行混了 35 条路由、启动流程和兜底游戏列表；`repository/postgres.ts` 873 行；`room-server/src/room.ts` 787 行兼座位、机器人、结算、视图。建议按 `routes/{auth,rooms,tasks,social,admin,internal}`、`repository/{wallet,settlement,tasks,leaderboard}`、`room/{seats,bot,view}` 拆。

**P2-3　插件并非运行时可插拔。** `plugins.ts` 静态 import 全部 13 个游戏，新增玩法要同时改代码、package.json 和 lockfile，与 README 宣称的「注册一行」不符。建议改为按 `services/games/*` 动态 `import()` 或读 `games.manifest.json`。

**P2-4　`apiVersion` 每个插件各写死 `= 1`。** `registry.ts:48` 的校验形同虚设——升级 `PLUGIN_API_VERSION` 时旧插件不会被拦截。改为由基类提供常量。

### 数据库与性能

**P2-5　排行榜名次每次全表窗口排序。** `postgres.ts:459-473`，`/api/profile` 每次访问都调。建议缓存名次（Redis 或物化表 + 定时刷新），或至少加 `(balance desc)` 部分索引。

**P2-6　缺索引与全表扫描。** `ledger` 缺 `(biz_type, created_at)`；`listRecords` 用 `jsonb_array_elements` 全表扫；`dailyWinners` 全表聚合。

**P2-7　内存仓储与 PostgreSQL 语义不等价。** `memory.ts:133-158` 结算后 `staked` 不清零，随后 `releaseOrphanBets` 会二次退款；`daily` 跨日不清零。降级模式本应是「可用的演示」，现在会产生与生产不一致的资金结果。

**P2-8　内存 Map 无上限。** `roomInvites`、`taskCells`、limiter 的清理策略只在超阈值时扫一次，长期运行会缓慢增长。

### 前端

**P2-9　首屏约 2.7MB 图片全量 eager 加载。** 13 张牌桌图约 1.8MB + `dealer-main.jpg` 796KB + `hero-table.jpg` 168KB。改法：`<img loading="lazy" decoding="async" width height>`（首屏前 3 张给 `eager`）、`index.html` 预加载 hero/荷官图、图片转 WebP（约省 60-70%）。

**P2-10　200ms 定时器驱动整桌重渲染。** `Baccarat.tsx:91`、`Dice.tsx:111`、`Tuizhuanzi.tsx:78` 用 state 存 `now`，每秒 5 次重建含路单和全部筹码的大子树。改法：1s tick + 倒计时交给 CSS 动画，或只在 `phase === 'bet'` 时启动。

**P2-11　无 ErrorBoundary，启动失败静默白屏。** `App.tsx:163` 的 bootstrap 只有 `catch {}`，任一游戏组件抛错整页白屏；断网时 `games=[]`，用户看到空大厅且无重试。改法：加边界 + 失败态重试按钮。

**P2-12　13 个游戏全进主 chunk + 单个 231KB CSS 阻塞首屏。** `Room.tsx:13-22` 静态导入。虽然当前 JS 只有 302KB（gzip 93KB）不算大，但按 `lazy()` 拆分游戏组件、开启 `cssCodeSplit` 后首屏解析还能再降一截。

**P2-13　若干交互缺陷。** 重连后离线队列会原样补发旧下注（`ws.ts:65-72`，应加 5s TTL 且只允许 Join/Ready）；表情气泡永不消失（`Room.tsx:382-388`，无退出动画与清理）；`/api/me` 401 后不清 token，每次启动都拿废 token 请求；iOS 输入框 `font-size: 13px` 会触发聚焦缩放（改 16px）；音频切歌存在竞态、filter 节点不 disconnect、无 `pagehide` 释放；输赢都播 `win` 音效（`App.tsx:234`）。

**P2-14　gomoku 搜索同步阻塞事件循环。** `gomoku:355-418` 每步做 8 层 VCF + alpha-beta + 每次扫 225 格评估，无时间预算，跑在 botTicker 里会卡住所有房间。改法：加 deadline（如 300ms）后返回当前最优，或搬到 Worker；蒙特卡洛限 100 次。

### 运维

**P2-15　`deploy.sh` 用 `. ./.env` 把配置当 shell 执行**（`deploy.sh:17-19`），`.env` 里一个反引号就能执行命令；解压直接覆盖、无上一版本回滚；重启前未 `chmod 600 .env`；无数据库备份。`setup-server.sh:33-35` 的密码拼进 SQL 且经命令行参数暴露（会进 shell history 与 `ps`）。建议：按键值解析 env、版本目录 + 软链切换、`pg_dump` 日备。

**P2-16　systemd 单元缺沙箱与资源限制。** 已有 `Restart=always` 且非 root（很好），建议补 `NoNewPrivileges=true`、`ProtectSystem=strict`、`PrivateTmp=true`、`MemoryMax`。
